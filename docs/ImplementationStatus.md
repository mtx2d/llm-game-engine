## Explicit limits and pending checks

Lua uses a configurable aggregate heap limit (64 MiB by default, including coroutine heaps) and a shared instruction budget of 1,000,000 per protected operation. Lua is built as C++ with its C API linkage preserved so allocation errors unwind engine RAII objects safely. Script source is limited to 1 MiB. Lua disables hooks inside `__gc` finalizers; the script environment rejects registering them so cleanup must use `OnDestroy`. These limits exclude engine asset allocations, and do not imply isolation between trusted project scripts sharing the same Lua state.

The static importer validates numeric JSON types before cgltf conversion, with a 64 MiB JSON and 128-level nesting limit. It rejects animation, skins, morph targets, compressed Draco/meshopt data, unsupported required extensions, and primitive modes other than triangles with descriptive errors. These limitations do not remove the requested static mesh/material/texture import gate. Physics rejects sheared or nonpositive world scales, nonuniform sphere/capsule scales, and dynamic bodies beneath another rigid body. The forward renderer currently bounds active lights to 32 and shadow allocation to 512 MiB. It uses one fitted directional shadow map without cascades, clamps filtering at point-shadow face edges, and excludes translucent surfaces from shadow casting and the depth/AO pass. Transparent primitives are sorted by their centers, so intersecting transparent geometry can sort incorrectly; transmission and refraction are not implemented. GPU submission currently waits synchronously each frame. These are enforced runtime limits, not claims of unrestricted support.

Scene environments use a project-relative HDR path, nonnegative intensity, and yaw in radians; an empty path disables IBL. CPU preprocessing uses bounded deterministic sampling and a versioned cache. Default output sizes are 32x16 irradiance, 128x64 specular with six roughness levels, and a 64x64 BRDF LUT at 256 samples. Image quality and production settings still need visual assessment on actual scenes.

NVRHI upstream primarily targets Windows/Linux. macOS requires deliberate MoltenVK portability handling and native validation. No Windows, macOS, or cross-platform release claim follows from Linux success or a CI configuration. GPU driver execution is kept out of the CPU sanitizer preset; renderer validation and readback are separate gates.
